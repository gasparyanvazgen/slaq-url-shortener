# ADR-002: `links` table schema, `CHECK` constraints, and schema bootstrap

- Status: Accepted
- Date: 2026-11-19
- Decision owner: User
- Register entry: D2 in [`DECISION-REGISTER.md`](DECISION-REGISTER.md)

## Context

The shortener needs one table, no relations, no accounts, and no per-click history. The shape must
make code uniqueness a storage guarantee rather than an application convention (D5, D6), store
timestamps in the canonical format fixed by D15, and keep expired rows readable (D7). The proposal
left the optional `CHECK` constraint set unresolved, and it was the last provisional part of the
schema. SQLite cannot add a `CHECK` constraint to an existing table without rebuilding it, so the
set had to be settled before the first `CREATE TABLE`.

## Decision

One table, created idempotently at startup:

```sql
CREATE TABLE IF NOT EXISTS links (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  code            TEXT    NOT NULL UNIQUE,
  original_url    TEXT    NOT NULL,
  is_custom       INTEGER NOT NULL DEFAULT 0
                          CHECK (is_custom IN (0, 1)),
  click_count     INTEGER NOT NULL DEFAULT 0
                          CHECK (click_count >= 0),
  created_at      TEXT    NOT NULL,
  expires_at      TEXT,
  last_clicked_at TEXT
);
```

- Generated codes and custom aliases share one namespace through `UNIQUE(code)`; the index is
  case-sensitive, matching the case-sensitive alias rule in D6.
- **The approved `CHECK` set is exactly `click_count >= 0` and `is_custom IN (0, 1)`.** Both are
  cheap invariants that a bug could otherwise violate silently and that are awkward to repair after
  the fact.
- The further checks proposed for this decision — `CHECK (original_url <> '')`,
  `CHECK (length(original_url) BETWEEN 1 AND 2048)`, `CHECK (length(code) BETWEEN 3 AND 32)`, and
  `CHECK (expires_at IS NULL OR expires_at > created_at)` — are **not** adopted. URL length and
  scheme are enforced where the input arrives (D18), and a duplicate length limit in the schema
  would be a second source of truth that must be kept in sync.
- `expires_at` is **not** indexed: expiry is evaluated per row on read, and there is no range query.
- Schema creation is `CREATE TABLE IF NOT EXISTS` run at startup. No migration framework in the
  MVP; no seed data, no views, no triggers.
- `id` keeps `AUTOINCREMENT`. With deletion out of scope (D9) rowid reuse cannot occur, but the
  column is an opaque surrogate key and the explicit keyword documents that it is never reused.

## Alternatives considered

- **The full six-check set**: catches more bad rows at the storage layer, but every one of the
  extra checks duplicates a rule already enforced in validation, and rotating the limit later would
  need a table rebuild. The user kept only the two invariants.
- **`original_url` in a separate table** (destination deduplication): would make repeated URLs share
  a row, contradicting D19's no-deduplication answer.
- **Separate `code` and `alias` columns**: two uniqueness rules, two lookup paths, and ambiguity
  about which one a request refers to.
- **Integer epoch timestamps**: faster comparisons and smaller rows, at the cost of unreadable
  records and a conversion at every boundary. D15 already fixed canonical ISO text.
- **A migration tool** (e.g. a versioned migration runner): the right call once a schema is
  deployed, but this schema has never run anywhere, so a version table and migration files would be
  ceremony with nothing to migrate.
- **`ALTER TABLE ADD CONSTRAINT` later**: not supported by SQLite for `CHECK`; any change to this
  set requires the twelve-step table rebuild, which is exactly why the set is settled now.

## Consequences

- Uniqueness and the two invariants hold even if a future code path skips validation.
- Alias length and URL length are application-enforced only; a direct database write could store an
  out-of-range value. Accepted, because nothing writes to this database except the repository.
- Changing the `CHECK` set later is a table rebuild — a real cost, recorded here so it is a
  deliberate change and not a surprise.
- The first deployed schema change is the point at which a migration mechanism becomes necessary.

- `TASKS.md` §2 creates the table with `UNIQUE(code)` and the two approved `CHECK` constraints.

## Verification

Schema review against SQLite's documented `UNIQUE` and `CHECK` semantics and `better-sqlite3`'s
`exec` for DDL. Nothing is installed and no database file exists, so no `CREATE TABLE` has run and
no constraint has been exercised. The first real check is a test that inserts `click_count = -1`
and `is_custom = 2` and expects a constraint error.
