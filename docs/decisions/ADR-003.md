# ADR-003: API routes and error envelope

- Status: Accepted
- Date: 2026-11-19
- Decision owner: User
- Register entry: D3 in [`DECISION-REGISTER.md`](DECISION-REGISTER.md)

## Context

The redirect route `GET /:code` takes the whole first path segment, so every other route competes
with it for that namespace. Clients also need one predictable failure shape: FR-08 and
`docs/requirements.md` require every error response to carry a stable machine-readable code. The
proposal offered a namespaced API and a single envelope but left both unapproved.

## Decision

Four routes:

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/links` | create a short link |
| `GET` | `/api/links/:code/stats` | read statistics for a code |
| `GET` | `/:code` | redirect to the stored destination |
| `GET` | `/health` | process liveness (D19) |

- Everything except the redirect lives under `/api`, and the static routes (`/health`, the `/api`
  router, the not-found handler) are registered **before** `/:code`, so a code can never shadow
  them.
- The create body accepts `url` (required), `alias` (optional), and `expiresAt` (optional).
- Every error response uses one envelope:

  ```json
  { "error": { "code": "VALIDATION_ERROR", "message": "…", "details": [ … ] } }
  ```

  `details` is optional and appears only on `400` validation failures, so `404` and `410` stay
  minimal.
- Status mapping: `400 VALIDATION_ERROR`, `400 RESERVED_ALIAS`, `404 NOT_FOUND` (unknown code and
  unmatched route), `409 ALIAS_TAKEN`, `410 LINK_EXPIRED`, `500 INTERNAL_ERROR` with a generic
  message.

## Alternatives considered

- **`POST /links` (no prefix)**: shorter, but every alias then has to be reserved against the route
  table, and a future `/links` page or `GET /links/:code` would collide with codes.
- **RFC 9457 `application/problem+json`**: a real standard with `type`, `title`, `status`, `detail`;
  more fields, a media type to document, and no MVP client to benefit.
- **Bare string or `{ "message": … }` errors**: smallest, but no stable code for a client to branch
  on, which FR-08 excludes.
- **Per-route error shapes**: lets each route be terse, but produces the inconsistency the
  requirement forbids.
- **A trailing catch-all registered before the static routes**: would swallow `/health`; ordering
  is the fix, and it is part of this decision.

## Consequences

- Aliases `api` and `health` must be reserved (D6), because both are real first segments under the
  redirect namespace.
- Adding a top-level route later means adding a reserved name in the same change.
- One error shape means the error middleware is the only place that writes an error body.
- `GET /api/links/:code/stats` yields to `/api` first, so a link whose code is `links` still
  redirects correctly at `/:code`.

## Implementation impact

- `src/modules/links/links.routes.ts` mounts under `/api/links`; `src/app.ts` registers `/health`,
  then the API router, then `/:code`, then the not-found handler.
- `src/middleware/error-handler.ts` and `src/middleware/not-found.ts` produce the envelope and the
  `404`.
- `src/lib/errors.ts` defines the application error types carrying `status` and `code`.
- `docs/api-specification.md` documents exactly these routes and codes; `docs/requirements.md`
  FR-07/FR-08 and `docs/testing-strategy.md` are aligned.

## Verification

Routing behavior is asserted from Express 5's documented static-before-parameter matching. No
server exists yet, so ordering, the envelope, and the not-found route are unproven. The first check
is the API test that requests `/health` while a link with code `health` cannot exist, plus a `404`
shape assertion.
