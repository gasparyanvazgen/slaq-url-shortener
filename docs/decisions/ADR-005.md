# ADR-005: Short-code generation (7-character Base62, five generation attempts)

- Status: Accepted
- Date: 2026-11-19
- Decision owner: User
- Register entry: D5 in [`DECISION-REGISTER.md`](DECISION-REGISTER.md)

## Context

Generated codes must be short, unguessable enough to resist trivial enumeration, and unlikely to
collide with each other or with user-chosen aliases, which share one namespace (D2, D6). The
proposal specified 7 Base62 characters and "retry up to five times" without saying whether that
meant five retries after the first attempt or five attempts in total.

## Decision

- Alphabet: `A–Z`, `a–z`, `0–9` (62 symbols); code length **7**; uniform random choice per
  character via `node:crypto`'s `randomInt(62)`. `Math.random` is never used.
- Uniqueness is enforced by `UNIQUE(code)` in the database, not by a pre-check.
- Collision handling: the generator is called and the insert attempted until it succeeds, for at
  most **five generation attempts in total** (the first attempt plus four retries). After the fifth
  failed insert the request fails with `500 INTERNAL_ERROR`.
- A custom alias never goes through the generator; its uniqueness comes from the same `UNIQUE` index
  and is reported as `409 ALIAS_TAKEN`.

## Alternatives considered

- **"Five retries after the first attempt" (six attempts)**: indistinguishable in practice at this
  scale, and it is what the original wording could be read to mean. Pinned to five total because
  the clarification the user approved says five attempts, and an ambiguous count in a bounded loop
  is exactly the kind of detail that becomes a dispute later.
- **Sequential integer codes (Base62-encoded)**: no collisions at all, shortest possible codes, but
  they leak creation volume and let anyone enumerate every link ever created.
- **Hash of the URL, truncated**: deterministic — the same URL yields the same code, which would
  reintroduce destination deduplication that D19 declined — and still collides after truncation.
- **A longer code (8–10 characters)**: fewer collisions, worse to read aloud; 62⁷ ≈ 3.5 × 10¹² is
  already far beyond this project's volume.
- **A shorter code (5–6 characters)**: more readable, but collisions arrive much sooner and retry
  pressure rises with every stored link.
- **`Math.random()`**: no dependency, but not cryptographically strong and not guaranteed uniform;
  `randomInt` is both.

## Consequences

- With 62⁷ possible codes, collisions are negligible at MVP scale; the retry loop is a safety net,
  not a load-bearing mechanism.
- Five attempts means a failure is possible in principle after a burst of insert conflicts; the
  answer is a generic `500`, which is the correct signal for "the server could not allocate a code".
- The generator is a pure function of randomness with no database access, so it is unit-testable in
  isolation; collision behavior is tested by injecting a generator stub.
- Codes are case-sensitive, consistent with the `UNIQUE` index and alias rules (D6).

## Implementation impact

- `src/lib/code-generator.ts` exports the alphabet, the length, and a `generateCode()` function;
  the alphabet is exported so tests can assert membership and length.
- `links.service.ts` owns the bounded attempt loop and translates exhaustion into
  `INTERNAL_ERROR`.
- `docs/testing-strategy.md` covers generator shape (length, alphabet, distribution sanity) and
  collision retry/exhaustion with a stubbed generator.
- `TASKS.md` §3 implements the generator and the retry loop.

## Verification

`crypto.randomInt(max)` is documented as uniformly distributed over `[0, max)`, and the uniqueness
guarantee comes from SQLite's `UNIQUE` index. No code exists, so neither was exercised. The first
checks are the generator unit test and a service test whose stubbed generator returns a conflicting
code five times and expects `INTERNAL_ERROR`.
