# ADR-007: Lazy expiration, `410 Gone`, and retained rows

- Status: Accepted
- Date: 2026-11-19
- Decision owner: User
- Register entry: D7 in [`DECISION-REGISTER.md`](DECISION-REGISTER.md)

## Context

Links may carry an optional expiry. Something has to decide what an expired link returns on
redirect, whether its click count keeps working, whether the row is deleted, and where the
expiry check lives. The project has no job runner, no scheduler, and a five-hour timebox, and
statistics for a finished campaign are still worth reading.

## Decision

- Expiry is evaluated **lazily**, at read time: on redirect and on statistics. There is no
  background job, scheduler, or sweep.
- A link is expired when `expiresAt <= now` (the boundary fixed by D15), evaluated with the injected
  clock.
- `GET /:code` for an expired link returns **`410 Gone`** with `LINK_EXPIRED` and does **not**
  increment `click_count` or `last_clicked_at`.
- `GET /api/links/:code/stats` for an expired link returns **`200`** with `isExpired: true` and the
  retained count (D17).
- Expired rows are **retained**; nothing deletes them.
- `expiresAt` must be **strictly in the future** at creation. A past or equal-to-now value is a
  `400 VALIDATION_ERROR`.
- `expiresAt` is stored as canonical UTC text (D15) and may be `NULL` for links that never expire.

## Alternatives considered

- **A cleanup job or scheduled sweep**: keeps the table small, but needs a scheduler, a failure
  mode, and a decision about what happens to statistics after deletion — and it deletes the history
  the product exists to show.
- **`404 Not Found` for expired links**: hides the reason and becomes indistinguishable from a typo
  in the code, which makes support and client behavior worse.
- **`403`/`451`-style "unavailable" statuses**: further from the semantics; `410` is exactly "this
  resource existed and is gone".
- **Deleting or soft-deleting on first expired access**: reclaims space, but destroys the count and
  makes the expired `200` statistics response impossible.
- **Eager expiration on create (rejecting already-expired links)**: not an alternative but a
  complement, kept and stated explicitly because the boundary test depends on it.

## Consequences

- No scheduler, no cron entry, no extra dependency; expiry correctness follows from one comparison
  at read time.
- The database grows with expired rows forever; accepted, since deletion is out of scope (D9) and
  there is no retention requirement.
- `410` reveals that a code once existed. Accepted for this product; the alternative leaks less but
  breaks statistics and diagnosability.
- Click counts stop at expiry, so statistics reflect clicks during the campaign only.
- Deterministic testing depends on the injected clock (D15); wall-clock reads are excluded.

## Implementation impact

- `links.service.ts` compares `expiresAt` with `clock()` and returns typed outcomes
  (`redirect | expired | notFound`) rather than throwing for `410`.
- `links.repository.ts` performs the conditional increment
  `WHERE code = @code AND (expires_at IS NULL OR expires_at > @now)`, so a link expiring between
  lookup and update increments nothing; `changes === 0` maps to `410`.
- `docs/database-design.md` documents the conditional update; `docs/api-specification.md` documents
  `410` on redirect and `200` + `isExpired` on statistics.
- `docs/testing-strategy.md` carries the eleven boundary cases; `docs/ai-workflow/TASKS.md` §6 implements them.

## Verification

Boundary semantics are fixed by D15 and the comparison is pure application logic over canonical
text. No code exists, so nothing ran. The first checks are the eleven expiry-boundary cases plus an
assertion that a redirect to an expired link leaves `click_count` unchanged.
