# ADR-009: Link deletion stays out of the MVP

- Status: Accepted
- Date: 2026-11-18
- Decision owner: User
- Register entry: D9 in [`DECISION-REGISTER.md`](DECISION-REGISTER.md)

## Context

The MVP has no accounts, no authentication, and no ownership model. It also retains expired rows so
statistics remain readable (D7). None of the ten MVP capabilities in `PROJECT.md` requires removing
a link.

## Decision

Deletion is **out of scope**. No `DELETE` endpoint, no `deleted_at` column, and no soft-delete
filtering in any read path.

## Alternatives considered

- **Hard delete (`DELETE /api/links/:code` → `204`)**: one route, one statement, but it adds an
  unauthenticated destructive capability — anyone holding a code could delete another person's
  link — and it contradicts retained statistics.
- **Soft delete (`deleted_at` + filters)**: preserves auditability, but every read path changes,
  the unique index semantics become ambiguous (can a deleted code be reused?), and the cost is
  roughly double a hard delete.
- **Documented manual database cleanup**: no code, no API surface, but nothing in the product
  supports it.

## Consequences

- Rows accumulate with no user-facing way to remove a mistaken link; acceptable for a portfolio
  MVP whose non-goals exclude accounts.
- Adding deletion later is additive: a new route plus, if wanted, `ALTER TABLE ... ADD COLUMN`,
  which SQLite supports without rebuilding the table.

## Implementation impact

- `docs/requirements.md` FR-09 states deletion is not in scope.
- `docs/api-specification.md` documents no delete route.
- `TASKS.md` keeps deletion in the deferred list.

## Verification

Scope review against `PROJECT.md` non-goals and the MVP capability list. No runtime artifact
exists to test; this is a scope decision.
