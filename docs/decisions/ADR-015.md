# ADR-015: Canonical UTC timestamps and the `expiresAt <= now` boundary

- Status: Accepted
- Date: 2026-11-18
- Decision owner: User
- Register entry: D15 in [`DECISION-REGISTER.md`](DECISION-REGISTER.md)

## Context

Timestamps are stored as text in SQLite and compared against a bound parameter to decide expiry.
Correctness depends on one fixed, unambiguous format and on a single source of "now" that tests can
control.

## Decision

- One stored format: `YYYY-MM-DDTHH:mm:ss.sssZ`, produced **only** by
  `Date.prototype.toISOString()` in application code, through an injected clock.
- SQL never calls `CURRENT_TIMESTAMP`, `datetime('now')`, `strftime()`, or `julianday()`.
- Input timestamps with an offset (for example `2026-12-31T00:00:00+02:00`) are accepted and
  normalized to the same instant in `Z`.
- A link is expired when `expiresAt <= now` (inclusive).
- `expiresAt` must be strictly in the future at creation, otherwise `400 VALIDATION_ERROR`.

## Alternatives considered

- **SQLite `CURRENT_TIMESTAMP`**: second precision, timezone-implicit, and untestable without
  freezing the database clock.
- **Epoch integers**: fast comparisons, opaque in the database and in API responses.
- **Storing local time or mixed offsets**: breaks lexicographic ordering and invites boundary bugs.

## Consequences

- Because the format is fixed-width UTC, lexicographic text comparison equals chronological
  comparison, so `expires_at > @now` is a valid SQL predicate.
- Response timestamps always carry milliseconds and `Z`, which the API contract (D17) states.
- Boundary behaviour is determined entirely by application code, so tests control it fully.

## Implementation impact

- `docs/database-design.md` records the format and forbids SQL date functions.
- `docs/testing-strategy.md` enumerates eleven boundary cases, all with a fixed clock.
- `TASKS.md` §6 injects the clock instead of calling `Date.now()` in services.

## Verification

`toISOString()` output and SQLite text comparison semantics are documented and deterministic;
registry-verified Zod 4 datetime handling supports offset input. Not yet executed — no
implementation exists.
