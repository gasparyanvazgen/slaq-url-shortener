# ADR-016: Native ESM

- Status: Accepted
- Date: 2026-11-18
- Decision owner: User
- Register entry: D16 in [`DECISION-REGISTER.md`](DECISION-REGISTER.md)

## Context

The stack (Express 5, Zod 4, Vitest, `tsx`) is ESM-friendly, and the ecosystem is moving away from
dual CJS/ESM packaging. Node's resolver is the runtime truth, so the compiler should match it
rather than abstract it.

## Decision

- `"type": "module"` in `package.json`.
- `module` and `moduleResolution` = `nodenext` (D10).
- Relative imports carry the `.js` extension even in `.ts` sources
  (`import { createApp } from './app.js'`).
- `import.meta.dirname` instead of `__dirname` / `__filename`.
- `tsx watch src/server.ts` in development; `node dist/server.js` in production.

## Alternatives considered

- **CommonJS**: no import extensions, `require` everywhere, but legacy and awkward with ESM-only
  dependencies.
- **Bundling with `tsup`/`esbuild`**: another build dependency and semantics that differ from the
  runtime.
- **`module: esnext` with `bundler` resolution**: permits extensionless imports that fail under
  Node at runtime.

## Consequences

- Every relative import needs an explicit `.js` extension; forgetting one fails at build or run
  time, which `nodenext` surfaces early.
- `@types/better-sqlite3` is a CJS `export =` package; TypeScript 6 forces `esModuleInterop`, so a
  default import works (D12).
- `eslint.config.js` is an ESM module (D11).

## Implementation impact

- `docs/coding-standards.md` states the import and path rules.
- `docs/ai-workflow/TASKS.md` §1 sets `"type": "module"` before any source file exists.

## Verification

Node ESM resolution rules and `import.meta.dirname` availability (Node ≥ 20.11) are documented;
the build and start commands are unproven until scaffolding.
