# ADR-019: Requirement-gap resolutions for the MVP contract

- Status: Accepted
- Date: 2026-11-19
- Decision owner: User
- Register entry: D19 in [`DECISION-REGISTER.md`](DECISION-REGISTER.md)

## Context

`docs/requirements.md` (Prompt 02, 2026-11-18) left four behaviors undecided because neither
`PROJECT.md` nor an approved decision settled them: unknown body fields (Q-2), duplicate
destination URLs (Q-3), `/health` scope (Q-4), and body-parser failures (Q-5). Each had a written
proposal, and each kept the acceptance criteria that depend on it from being treated as settled.
Deletion (D9) was reopened for confirmation during the same review.

## Decision

The user adopted the proposed default for all four gaps on 2026-11-19 and reconfirmed that deletion
stays out of the MVP.

- (a) **Unknown body fields** — ignored (stripped), never rejected; only `url`, `alias`, and
  `expiresAt` are read, and nothing else is stored.
- (b) **Duplicate destinations** — no deduplication: every successful create stores a new row with
  a new code, so the same URL created twice yields two links with two distinct codes.
- (c) **`/health` scope** — process liveness only: no database query, no readiness state, no `503`.
  This fixes the endpoint's behavior; whether `/health` is registered at all still belongs to D3.
- (d) **Body-parser failures** — malformed JSON and payloads above the body-parser limit map to
  `400 VALIDATION_ERROR` in the shared envelope. Express's default body limit is kept, and no `413`
  status or new error code is introduced.
- (e) **Deletion** — unchanged: out of scope per D9 ([`ADR-009.md`](ADR-009.md)), now explicitly
  reconfirmed.

## Alternatives considered

- **Reject unknown fields with `400`** (strict schema): catches client typos, but breaks
  forward-compatible requests and adds a failure mode the MVP does not need.
- **Deduplicate by destination**: saves codes and makes repeated creates idempotent, but requires a
  lookup on `original_url`, a second response case for "already existed", and an answer to whether
  one link's expiry applies to another's — real complexity for a five-hour MVP.
- **Readiness probe in `/health`**: useful behind a load balancer, but the MVP is not deployed, and
  a probe would make the endpoint fail when the database is unavailable, hiding the difference
  between a dead process and a locked database.
- **`413 Payload Too Large`**: more precise, but adds an error code, a table row, and a client
  branch for a case no MVP client exercises; the shared `400` envelope keeps one error shape.
- **Reopening deletion**: needs an unauthenticated destructive endpoint and contradicts retained
  statistics (D7); the user declined.

## Consequences

- The create contract never answers `413`, and a strict-schema client is not part of the contract.
- Repeated destinations accumulate rows; `code` remains the only uniqueness key.
- `/health` cannot serve as a readiness check; proving the database works requires an API call.
- Every acceptance criterion that cited Q-2 … Q-5 now cites D19, so the only provisional items left
  in `docs/requirements.md` are those resting on D1–D7.

## Implementation impact

- `docs/requirements.md`: FR-01, FR-07, FR-08, and FR-10 carry the answers, checked by AC-01.9,
  AC-01.10, AC-07.7, and AC-08.6.
- `docs/api-specification.md`: the create field rules, the health description, and the error table
  reflect the answers.
- `docs/testing-strategy.md`: adds unknown-field, duplicate-destination, oversized-body, and
  health-without-database cases.

## Verification

Documentation review only. Nothing is implemented and no `package.json` exists, so no test ran. The
Express `express.json()` default limit (100 kB) and the `body-parser` failure types are asserted
from framework defaults and must be confirmed when the middleware is written.
