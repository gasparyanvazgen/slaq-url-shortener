# ADR-020: Redirect write path and click-count semantics

- Status: Accepted
- Date: 2026-11-19
- Decision owner: User
- Register entry: D20 in [`DECISION-REGISTER.md`](DECISION-REGISTER.md)

## Context

D7 approved a conditional click increment and the `docs/database-design.md` query pattern described
it as running "inside a transaction and inside the same `try` as the lookup". The Prompt 03
architecture review found two problems with that phrasing.

First, the transaction adds nothing. The expiry guard is already part of the statement —
`WHERE code = @code AND (expires_at IS NULL OR expires_at > @now)` — so the increment is atomic on
its own. With one process, one connection, and a synchronous `better-sqlite3` driver, no other
statement can interleave between the lookup and the update. `db.transaction()` would add a
`BEGIN`/`COMMIT` pair to the hottest path and imply a correctness dependency that does not exist.

Second, Express routes `HEAD` requests to the `GET` handler when no `HEAD` route is registered. A
monitoring probe or a prefetch that sends `HEAD /:code` would therefore increment `click_count`,
inflating statistics that are supposed to count redirects.

## Decision

- The redirect path loads the row to distinguish `404` from `410`, then runs the single guarded
  update **without** an explicit transaction:

  ```sql
  UPDATE links
     SET click_count = click_count + 1,
         last_clicked_at = @now
   WHERE code = @code
     AND (expires_at IS NULL OR expires_at > @now);
  ```

- `changes === 0` means the link expired (or vanished) between the lookup and the update; the
  response becomes `410 LINK_EXPIRED`, or `404` if the lookup found nothing. No count is lost or
  double-counted either way.
- `HEAD /:code` answers with the same status and `Location` as `GET` but does **not** increment
  `click_count` or `last_clicked_at`. Only `GET` counts as a click.
- The service still decides expiry from the row and the injected clock; the repository guard is the
  backstop for the race between the two statements.

## Alternatives considered

- **Keep the explicit transaction**: harmless in isolation, but it implies the increment depends on
  transactional isolation when the `WHERE` clause already provides the guarantee, and it widens the
  repository surface for no observable behavior change.
- **Increment on `HEAD` too**: simplest code — just register `GET` and let Express handle `HEAD` —
  but makes public statistics depend on probe behavior outside the product's control.
- **A single `UPDATE … RETURNING original_url`**: atomic and single-statement, but an empty result
  cannot distinguish `404` from `410` without a second read, so it trades one statement for an
  ambiguous status code.
- **Increment before the expiry decision**: would count attempts rather than redirects, contradicting
  D7 and FR-04.

## Consequences

- The hottest path is one lookup plus one guarded update, with no transaction overhead.
- Click counts reflect issued `GET` redirects only; `HEAD` probes cannot inflate them.
- The status distinction between unknown and expired codes survives, because the lookup still
  precedes the update.
- Any future write that needs multi-statement atomicity must introduce an explicit transaction
  deliberately; this ADR does not forbid transactions in general.

## Implementation impact

- `src/modules/links/links.repository.ts` exposes `findByCode(code)` and
  `incrementClick(code, nowIso)`, the latter returning the number of changed rows.
- `src/modules/links/links.service.ts` maps `changes === 0` to the expired outcome.
- `src/modules/links/links.routes.ts` registers the `GET` handler and a `HEAD` handler that reuses
  the redirect outcome without the increment (or the controller checks `req.method`).
- `docs/database-design.md` documents the query without a transaction; `docs/requirements.md`
  FR-04 and NFR-06, `docs/api-specification.md`, `docs/testing-strategy.md`, and `TASKS.md` §4
  reflect the decision.

## Verification

Review of the statement against SQLite semantics: a single `UPDATE` with a `WHERE` predicate is
atomic, and `changes` reports rows matched and modified. No code exists, so nothing ran. The first
checks are a repository test asserting `changes === 0` for an expired row and an API test asserting
that `HEAD /:code` returns `302` while `click_count` stays unchanged.
