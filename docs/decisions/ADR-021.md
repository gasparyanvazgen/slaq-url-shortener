# ADR-021: `SQLITE_BUSY` handling

- Status: Accepted
- Date: 2026-11-19
- Decision owner: User
- Register entry: D21 in [`DECISION-REGISTER.md`](DECISION-REGISTER.md)

## Context

`docs/database-design.md` left one question open: how to handle `SQLITE_BUSY` beyond
`busy_timeout = 5000` — retry once, or surface `500`? The MVP runs one synchronous process with one
connection, so the application itself cannot produce lock contention. The only realistic source is
an external writer holding the write lock, for example an operator running `sqlite3` against the
database file.

The question had to be settled before implementation because it determines whether the repository
contains a retry loop, and because the error middleware needs to know which failures are expected.

## Decision

- **No retry.** When `busy_timeout` elapses and `better-sqlite3` raises `SQLITE_BUSY`, the
  centralized error middleware maps it to `500 INTERNAL_ERROR` with the generic message already in
  the contract.
- The underlying driver error (including the SQLite code) is logged server-side and is never sent to
  the client.
- `busy_timeout` stays at `5000` ms; the pragma is the only waiting mechanism.
- No new error code, status code, dependency, or configuration knob is introduced.

## Alternatives considered

- **Retry once**: absorbs a brief external lock, but doubles the worst-case wait to about ten
  seconds and adds a second failure path to the redirect route for a condition that should not occur
  in normal operation.
- **Retry with backoff**: the right answer for a multi-writer service; more surface than a
  single-process MVP needs.
- **Lower `busy_timeout` to fail fast**: turns brief external locks into user-visible `500`s and
  makes the behavior depend on an arbitrary timeout value.
- **A `503` "database busy" response**: a new status and error code for a case the contract does not
  model, and misleading for a liveness-only health endpoint.

## Consequences

- A rare external lock surfaces as a generic `500`; clients see the same failure shape as any other
  unexpected error.
- No retry loop means no latency amplification and no partial-write ambiguity on the redirect path.
- If the service ever gains a second writer or multiple processes, this decision must be revisited
  with a new ADR.

## Implementation impact

- `src/db/connection.ts` keeps `busy_timeout = 5000`.
- `src/middleware/error-handler.ts` recognizes the driver's busy error and answers
  `500 INTERNAL_ERROR` without echoing the SQLite code or message.
- `docs/database-design.md` records the policy and no longer lists the question as open;
  `TASKS.md` §2 and `docs/testing-strategy.md` carry the corresponding item and test note.

## Verification

Documentation review only: `better-sqlite3` surfaces `SQLITE_BUSY` as a driver error after
`busy_timeout`, and the existing middleware is the single error writer. No code exists, so nothing
ran. Because a genuine busy database needs a second connection, the planned check injects a
repository that throws a busy error and asserts the `500` envelope shape and a generic message.
