# ADR-022: `PORT` default and startup parsing

- Status: Accepted
- Date: 2026-11-19
- Decision owner: User
- Register entry: D22 in [`DECISION-REGISTER.md`](DECISION-REGISTER.md)

## Context

`docs/requirements.md` FR-11 confirmed startup configuration under D17, which settles
`PUBLIC_BASE_URL` (validation, normalization, development default, production fail-fast) but says
nothing about `PORT`. FR-11 nevertheless stated that `PORT` defaults to `3000` and must be an
integer in 1–65535, and marked that sentence as "(proposal; no decision records a default)" — the
last unsourced value in an otherwise confirmed requirement.

The gap mattered for three concrete reasons:

- D17's development default is `http://localhost:${PORT}`, so `PORT` decides what that default
  resolves to. Leaving it undefined left a confirmed acceptance criterion (AC-11.4) resting on an
  unapproved value.
- D17's `PUBLIC_BASE_URL` policy is environment-dependent (development default, production
  fail-fast), so "does the `PORT` default apply in production too?" was genuinely ambiguous.
- Without a parsing rule, an implementation could plausibly use `parseInt`, which silently accepts
  `3000abc` as `3000`, or accept `0`, which binds an OS-assigned ephemeral port and would make the
  development `PUBLIC_BASE_URL` default point at a dead port.

## Decision

- `PORT` is read once at startup, **trimmed**, and resolved before any listener is created.
- **Unset, or empty after trimming → `3000`, in every environment.** One rule; no `NODE_ENV`
  branch, and `NODE_ENV` does not affect the result.
- When set, the trimmed value must consist **only of ASCII digits `0`–`9`**, and its decimal
  numeric value must be within **1–65535 inclusive**. No trimming beyond the outer whitespace rule,
  no sign, no decimal point, no exponent, no separators, no non-ASCII digits; values are never
  parsed with a prefix-coercing `parseInt`.
- **Leading zeros are allowed**, because the input is still all ASCII digits and its numeric value
  is what matters: `PORT=03000` resolves to port `3000`, and `PORT=00001` resolves to `1`.
- **`0000` is rejected**, because its numeric value is `0`, which is outside 1–65535. `PORT=0` is
  rejected for the same reason: it would mean "let the OS choose", which makes the bound port
  unpredictable and falsifies the development `PUBLIC_BASE_URL` default (`http://localhost:0`).
  Nothing needs an ephemeral port, because no test binds a port (D8, NFR-08).
- An invalid value **aborts startup before `listen` in every environment**, with a log line naming
  `PORT` and the failed rule. The raw value is not echoed (NFR-07).
- `PORT` has exactly two uses: the value passed to `listen`, and the source of D17's development
  `PUBLIC_BASE_URL` default. It is never consulted per request and never appears in any response.
- No `HOST` or bind-address variable is introduced; the server's default binding is unchanged and
  remains undocumented.

## Alternatives considered

- **Development default `3000`, `PORT` required in production** (symmetry with D17): catches a
  deployment that forgot the variable. Rejected because it adds a second environment-dependent
  branch and a second failure mode to protect against a failure that is immediately visible — a
  wrong port is unreachable, not silently wrong, and it corrupts no stored data. Production
  deployment is an explicit non-goal, and hosting platforms inject `PORT` anyway.
- **`PORT` required in every environment**: fully explicit, but `npm run dev` then fails on a fresh
  clone until `.env` is copied, which works against `PROJECT.md`'s "install, run, test, and
  understand" reviewer criterion.
- **Accept `0` for an OS-assigned port**: convenient in principle, but no test binds a port and it
  breaks the development `PUBLIC_BASE_URL` default.
- **`parseInt(value, 10)` with a range check**: shorter to write, but accepts `3000abc` as `3000`
  and `3000.9` as `3000`, turning a configuration typo into a silently different port.
- **Reject leading zeros**: a stricter canonical form, but needless — the numeric value is
  unambiguous, and the approved rule above already excludes everything that is not a port number.

## Consequences

- `npm run dev` and `npm start` work with no `.env` present, always on `3000` unless overridden.
- A malformed `PORT` fails loudly and early in every environment, with the same message shape as
  `PUBLIC_BASE_URL` failures.
- `PORT` is a pure startup value: no runtime branch reads it, so configuration tests can assert it
  without an HTTP server.
- If production hosting ever becomes in scope, this decision may need revisiting; that would require
  a new decision and a new ADR.

## Implementation impact

- `src/config.ts` resolves `PORT` (trim → default `3000` → ASCII-digit check → 1–65535) alongside
  `PUBLIC_BASE_URL`, and the resolved number is part of `config`.
- `src/server.ts` passes `config.port` to `listen` and builds the development `PUBLIC_BASE_URL`
  default from it.
- `docs/requirements.md` FR-11 no longer contains a proposal and carries AC-11.6 … AC-11.10.
- `docs/security-guidelines.md`, `docs/coding-standards.md`, and `docs/testing-strategy.md` record
  the parsing rule and its test cases.

## Verification

Documentation review and reasoning only: no `package.json`, `src/`, or test file exists, so nothing
ran. The rule is pure string handling and will be proven by configuration unit tests (default, trim,
`03000` → `3000`, `00001` → `1`, `1` and `65535` accepted, `0`, `0000`, `65536`, `-1`, `+3000`,
`3000.5`, `1e3`, `abc`, `3000abc` rejected) plus a startup test that asserts no listener is created
for each rejection.
